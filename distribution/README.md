# Verification Platform distribution

This directory belongs to the single platform set identified by `resource-index.json`. It is not a separate package release. Installed resource paths are relative to this directory. Both frontend skills in `dist/frontends/` link to the same `dist/runtime/` host/CDP implementation and share evidence/reconciliation.

Install exact locked dependencies explicitly with `npm ci --ignore-scripts`; no browser download is required for the controlled distribution check. Runtime execution never installs dependencies. `npm test` runs only the synthetic ordinary Playwright Test/evidence/reporter compatibility smoke, not a browser experiment or consumer proof. Run from the unpacked distribution root. TypeScript declarations accompany public JS entries. The Python and PowerShell host assets are siblings under `dist/runtime/host/wsl-windows`; the shell native compatibility entry retains executable mode. Host execution still requires assigned external Windows runtime/configuration and Python/PowerShell prerequisites.

Supply the exact neutral binding and explicit root/index path to the `./resources` public export. Planning mode validates normative dependency closure; execution validates every indexed runtime/frontend resource. The validation CLI is `node dist/src/validation/cli.js` with JSON stdin. Result validation is `node dist/src/validation/result-cli.js`. There is no checkout/global-skill/latest fallback.

An offline snapshot retains the identical index bytes and all normative resources. It supports planning validation only; missing runtime/frontends cannot satisfy execution resolution. Evidence summary contracts preserve environment-specific capability limitations. Development observations, consumer artifacts, migration provenance and downstream overlays are excluded.

Release assembly and dry-run procedures are included in `distribution/RELEASE.md`; release-support commands run from canonical source. Synthetic fixture metadata is test-only and authorizes neither publication nor project adoption.

## Installation and consumer adoption

Platform installation and consumer operational readiness are separate requirements. Successful installation/adoption requires both. Copying release files, binding the release, validating integrity, or installing frontend skills/agents alone is installation-only state and must not be reported as completed adoption or PASS.

For an authorized installation or upgrade, the installer (including an AI installer) must complete this procedure:

1. Install the exact published distribution, prepare its locked dependencies explicitly, bind the selected release and validate full execution integrity. Configure both frontend skills and matching browser-agent paths through the consumer's existing installation workflow. Preserve indexed platform files.
2. Inspect only current native consumer sources needed to realize and validate integration from these installation/adoption instructions, the pinned Verification Integration Contract and public contracts. Do not derive new requirements from consumer plans/obligations or previous generated integration. Follow existing authorization and preserve native semantics.
3. Regenerate all required integration under `.verification/integration/` on install, upgrade and recovery. Realize required configuration and callable exports; planned references alone are insufficient. Check assigned host/runtime prerequisites, effects, ownership and authorization. Keep integration outside the indexed platform distribution; never add consumer-specific behavior to the platform.
4. ProjectPreflightHook remains optional, never universally required. Create or update one only when the consumer project actually needs deterministic project-specific readiness checks beyond the shared preflight. Before authoring/updating it, read the complete [ProjectPreflightHook consumer authoring contract](../contracts/contracts.md#projectpreflighthook-consumer-authoring-contract) in the pinned distribution. If required, use generated installer-owned code under `.verification/integration/` and the public hook contract; reference it from consumer runner/fixture configuration with the current entry digest, version, input and deadline, never from the neutral platform binding. If no such checks are needed, omit the hook and record that determination. Hook execution observes readiness; it does not perform persistent setup or replace required human action.
5. Establish consumer operational readiness with the smallest checks sufficient for its applicable Verifier workflow, reusing still-valid evidence. Check actual configured imports/exports and configuration against current Platform requirements and native sources; a distribution smoke test proves only platform compatibility. Any necessary execution or environment check remains subject to the project's existing authorization. Do not silently assume readiness from static configuration when an unresolved prerequisite needs an observation or human action. Adoption readiness is separate from product proof and human acceptance; it neither establishes product PASS nor authorizes live acceptance.
6. When no HITL is pending, report platform installation and consumer operational readiness separately, including the inspected sources, integration regenerated, hook decision and readiness evidence. Report adoption PASS only when the matching platform is installed and the consumer repository is operationally ready for its applicable Verifier workflow. If an unresolved project decision, missing prerequisite, required authorization or human action prevents establishing operational readiness, report adoption BLOCKED with the specific outstanding requirement and its owner/next action, even when platform installation succeeded. Do not silently stop at installation or fabricate configuration to obtain PASS.

The orchestrator's [packaged installation/adoption entry](../dist/frontends/verification-orchestrator/assets/installation-adoption.md) supplies the checkpoint/resume procedure and public helper calls. `/invocation` exports `installedHookSelfCheck`, `invokeReadiness` and the adoption checkpoint/assessment helpers. Installed `npm test` includes the indexed synthetic hook mechanism check; consumer READY is established separately through the actual configured fixture/runner. Readiness summaries do not emit product results. Continue revised diagnosed authorized adaptations after reconciliation and a fresh affected check. Technical incompatibility or a repeated defect ID alone does not require HITL/BLOCKED; unchanged failures are not retried.

Installation BLOCKED/HITL, missing/incompatible artifacts, unresolved implementation choices and failed intermediate checks are nonterminal. The installer creates/updates required installer-owned integration itself when safe and authorized. When continuation requires a user-owned decision, authorization or action, present concrete viable resolution options, always include explicit cancellation of the entire Verifier installation, and wait for the user's decision. After approval of a non-cancel option, implement it and continue the same installation, verifying any action only its owner can perform. Only verified adoption PASS or explicit user cancellation ends installation; cancellation grants no rollback/uninstall or browser-cleanup authority. Required setup/remediation is performed by the installer outside the observation-only hook. Product proof semantics remain unchanged.

Before HITL, exhaust safe and authorized autonomous resolution: reuse authoritative configuration, derive selected values, discover supported current state, regenerate integration, and create/update installer-owned integration within existing authority. Validate the resulting state. A missing technical value alone does not justify HITL. Do not request discoverable/derivable raw technical values such as paths, executable paths, IDs, URLs or configuration filenames.

Each HITL addresses exactly one current unresolved user-owned issue (decision, authorization or external action). Investigate the actual available solutions first and present concrete outcome choices. Each non-cancel option states its outcome, material consequences and the installer's technical implementation within verified authorization. Always include exactly one cancellation option whose description is exactly **Cancel Verifier installation**. Skip, Ignore, Continue partially configured and Continue without required readiness are invalid readiness-bypass substitutes.

For a required external artifact/capability the installer cannot create under current authority, identify the missing prerequisite, external action and owner. Keep the request pending until the user reports completion; then the installer must discover and validate the resulting state before advancing. Do not request transcription of discoverable technical details. After an approved outcome, persist the matching resolution before implementing installer-owned work. After every autonomous or user-approved resolution, validate and reassess before any subsequent HITL; selected outcomes may determine several derived values and eliminate later questions. Reuse unaffected valid evidence and allocate fresh affected checks when required; do not pre-build a questionnaire, condition queue or fixed prerequisite checklist.

At the caller's actual outgoing interaction boundary, use `adoptionResumeAction`/`pendingHITL`: **pending HITL → emit/present only the recorded current HITL → return and wait; otherwise → normal report**. The HITL branch must not fall through to normal reporting. Include only context necessary for the current decision/action and its exact cancellation option; never mix progress/results with a HITL response. Keep detailed progress/diagnostics in existing evidence and report them separately after resolution. On resume, present the restored request unchanged and wait for the explicit decision or requested external-action completion report. This repository delegates emission to the AI/caller; checkpoint validation cannot control arbitrary caller prose.

Platform defines WHAT consumer integration must satisfy; the AI installer determines HOW from the current packaged contract and current native consumer sources. Native consumer code/configuration is the semantic authority. On every install, upgrade and recovery, freshly regenerate all required integration under `.verification/integration/`, even when old generated wiring appears valid. All integration-only files, including runners, fixtures, providers/declarations, readiness entries/probes, hooks, adapters and auxiliary bridges, are installer-owned generated output in this single directory. Previous generated integration has no preservation or requirement authority. Autonomously adapt/wrap/bridge/rewire technical incompatibilities within existing authorization. Confine writes by realpath; an escaping symlink is not ownership. Preserve native semantics, installed Platform bytes, checkpoint/approvals and retained evidence. No ownership registry, migration or old-layout cleanup is required. Reconcile active dispatches and reserved correction postconditions before replacing code; never replace code used by a running attempt. Recovery must freshly derive integration even after a completed configuration stage; identical current bytes may reuse still-valid evidence, while changed sources/configuration require fresh affected checks.
