# Verification Integration Contract — format 1

This development resource is platform-owned and process-independent. Installation or publication is not implied. A consuming process must classify irreducible browser/native proof from governing obligations, supply traceable required claims, and preserve all mandatory proof, human obligations, prerequisites and environment pairs. File type alone does not establish applicability.

Use the single indexed `schemas/browser-verification-plan.schema.json`. Stable claim IDs reference governing source IDs, expected behavior and mandatory proof IDs. Prerequisite references are metadata, not executable scheduling. Plans contain no action language, approval booleans, outcomes, secrets or live endpoints. Planned configuration references are valid at planning; execution requires realized configuration and real callable exports. Structural validity cannot resolve materially missing behavior or establish semantic proof fitness.

Resolve `.verification/platform.json` through the exact repository, platform tag, source commit and SHA-256 resource index. Normative dependencies are recursively indexed. Planning may use a normative-only snapshot of that same release. Execution requires the complete matching indexed distribution. Missing/mixed/unsupported content blocks use; no latest, global installation or development-checkout fallback is permitted. Local paths are resolution configuration, not normative identity. Explicit upgrades change the binding.

Installation/adoption requires both platform installation and consumer operational readiness. After installing, upgrading or recovering, inspect only the current native consumer sources needed to realize and validate the current Platform integration requirements; regenerate necessary installer-owned execution/readiness integration. Release files, binding/integrity and frontend skills/agents alone cannot establish adoption PASS. PASS requires the consumer repository to be operationally ready for its applicable Verifier workflow; unresolved project decisions or required human actions that prevent readiness produce adoption BLOCKED. ProjectPreflightHook remains optional: create/update it only when deterministic project-specific readiness checks are needed, with project semantics and configuration owned by the consumer. Adoption readiness does not establish product proof or human acceptance.

Installation BLOCKED/HITL and failed intermediate checks are nonterminal. Missing or incompatible consumer integration is created/updated by the installation agent when safe and authorized. Required user-owned decisions, authorization or actions must be presented as concrete viable resolution options including explicit cancellation of the entire Verifier installation; wait for the user's decision. After approval of a non-cancel option, the installer implements it within authorization, verifies owner-exclusive actions and continues the same installation. Only verified adoption PASS or explicit user cancellation terminates installation. Setup/remediation takes place outside the observation-only ProjectPreflightHook; cancellation does not grant uninstall, rollback or browser cleanup permission.

Generic capabilities suffice when their actual sources establish the obligation; then create no project proof/instrumentation hooks. Required internal sources use the smallest separately authorized project provider observing the real boundary and declaring effects/provenance. A missing generic capability is a platform dependency, not permission to instrument an application. Planned/unestablished capabilities are unavailable for generation.

Before selecting or using any concrete browser, browser version, profile, site or account for verification, obtain explicit user approval of the proposed selection. The AI may autonomously discover suitable candidates and derive their technical details, but must not commit to or use a candidate before approval. Present the concrete proposed browser/runtime, version, profile, site and account together as one authorization decision; do not ask the user to supply discoverable technical values. Honor explicit user/task constraints when preparing the proposal. Reuse existing explicit user approval only when it covers the exact proposed selection; discovery, task constraints, automatic approval review and elapsed time are not selection approval. After approval, record the approved selection and its observed source in the existing assignment/configuration and evidence, then continue through the existing Platform configuration, Host Runtime / BrowserPreflight identity validation and continuity guarantees. Selection approval does not authorize other restricted actions or change claims, expected behavior or required environment coverage. Do not silently substitute an environment during proof; a changed selection requires explicit user approval.

The caller supplies exact plan/binding digests and authorization tied to those identities, explicit provider/fixture configuration, assignment, allowed effects, ownership, evidence constraints and output location. Assignment may restrict allowed effects; it cannot expand the plan or remove obligations. The platform neither grants permissions nor interprets a process approval registry. Missing material normative behavior returns to its owner.

Execution supports only WSL Node/Playwright → Windows headed Chrome/PowerShell/UIA. One worker, no full parallelism, zero retries and exclusive caller assignment apply to a shared desktop. Persistent browser/profile/pages remain borrowed. Tests use ordinary TypeScript Playwright assertions/fixtures. No alternate driver, action interpreter, automatic installation, replay or fallback is permitted.

Every required `(claimId, environmentId)` remains in the manifest/result even if blocked, skipped or filtered. Complete identity-bound mandatory evidence establishes PASS. Sufficient contradiction establishes FAIL. Unavailable prerequisites before relevant attempt establish BLOCKED. Missing/lost/stale/inadequate evidence after attempt, or absent attempt knowledge, is INCONCLUSIVE. Aggregate precedence is FAIL → BLOCKED → INCONCLUSIVE → PASS. Runner exit/status are separate. Preserve decisive contradictions and collection/cleanup limitations; proof-relevant failed cleanup invalidates affected proof. Completion and human acceptance remain the caller's authority.

See [contracts](contracts.md) for callable and serialized boundaries; all normative dependencies must be indexed together.

Before product proof, the shared runtime executes BrowserPreflight → optional ProjectPreflightHook → TargetPreflight → ENVIRONMENT READY. Existing assigned launch, exact host configuration, exclusive ownership and allowed effects remain authoritative. Known required host escalation is obtained by the caller before invoking restricted operations. The readiness hook is explicitly referenced from caller runner/fixture configuration, not `.verification/platform.json`, and runs deterministic installer-generated integration code under `.verification/integration/` with contract version 1, expected entry digest, JSON input and a bounded deadline. Project readiness semantics belong to the project; the platform owns invocation and evidence handling.

Missing normal pages can be created/navigated only with `target-create` and `target-navigate` permitted by the relevant normative claims and assignment, and literal `target` disposable ownership. All observable browser state produced or changed during a test cycle, including created pages, is preserved after proof/test execution and setup failure. Normal proof assignments use `ownership.cleanup=[]` for browser targets; ordinary teardown never invokes target disposal, even if a legacy assignment includes `target` cleanup authorization. Browser-state cleanup/reset is an explicit lifecycle action only: before a new cycle requiring a clean baseline, or when explicitly terminating the overall verification/browser session according to session policy. Low-level disposal remains available with literal `target` cleanup authorization for those actions. Temporary verifier connections may be disposed without changing observable browser state. Browser/profile and reused pages remain borrowed. Persisted preflight records are separate from product Evidence/Result; known blocked setup produces unattempted blocked claim records and proof NOT RUN, preserving actual runner status. READY alone never establishes product PASS. No transparent identity replacement or setup recovery occurs during an atomic proof.

Platform defines WHAT consumer integration must satisfy; the AI installer determines HOW from the current packaged contract and current native consumer sources. Native consumer code/configuration is the semantic authority. On every install, upgrade and recovery, freshly regenerate all required integration under `.verification/integration/`, even when old generated wiring appears valid. All integration-only files, including runners, fixtures, providers/declarations, readiness entries/probes, hooks, adapters and auxiliary bridges, are installer-owned generated output in this single directory. Previous generated integration has no preservation or requirement authority. Autonomously adapt/wrap/bridge/rewire technical incompatibilities within existing authorization. Confine writes by realpath; an escaping symlink is not ownership. Preserve native semantics, installed Platform bytes, checkpoint/approvals and retained evidence. No ownership registry, migration or old-layout cleanup is required. Reconcile active dispatches and reserved correction postconditions before replacing code; never replace code used by a running attempt. Recovery must freshly derive integration even after a completed configuration stage; identical current bytes may reuse still-valid evidence, while changed sources/configuration require fresh affected checks.
