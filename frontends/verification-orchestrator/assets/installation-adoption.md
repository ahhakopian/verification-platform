# Installation / Adoption entry

Use this entry for an explicitly authorized install or upgrade. Maintain one active installer and exclusive access to the assigned desktop. Installation permission does not authorize browser launch, target creation/navigation, persistent setup or product changes. Obtain the consumer's existing authorization/HITL before those effects.

## Inputs and owned files

Select an exact published release and full local distribution root/index. Read the current packaged Platform requirements and only the native consumer sources needed to realize and validate them. Never edit indexed published platform content.

Before authoring or updating a consumer hook, read `<distribution>/contracts/contracts.md`, section **ProjectPreflightHook consumer authoring contract**. That indexed public contract supplies the complete existing hook requirements, including exact shapes, validation, lifecycle and effects. No source architecture checkout or `examples/` is required; the synthetic canary is not a consumer-hook substitute.

Use the distribution's public `/resources`, `/validation`, `/compilation` and `/invocation` entries. The corresponding installed JS paths are `dist/src/resources/resolve.js`, `dist/src/validation/plan.js`, `dist/src/compilation/bundle.js` and `dist/runtime/invoke.js`. Run commands from the consumer root with explicitly assigned inputs. No development checkout or personal/global skill path is a fallback.

The consumer-local checkpoint is `.verification/adoption.json`; `.verification/platform.json` remains only the binding. Detailed observations and attempt history belong in evidence/output files, outside the installed distribution. References include path and SHA-256. Define the checkpoint's input fingerprint from the exact applicable Platform requirement/native source/plan/configuration bytes and selected binding. Reassess affected stages when those inputs change.

## Procedure

1. **INSTALL / UPGRADE:** use the consumer's existing release installation convention, explicitly prepare locked dependencies, and call `resolveResources(binding,{root,indexPath,mode:'execution'})`. Check matching frontend/agent paths. Record inspected identity and integrity evidence. Do not select latest, install providers automatically, or mutate release files.
2. **CONFIGURE CONSUMER:** freshly regenerate entry, fixture, runner/config, setup-only probe, provider wiring and required adapters/bridges under `.verification/integration/` from current authorities/native sources. Discover configured callable exports/declarations through `discoverProviders`, and perform project-compatible validation/typechecking. Establish `{state,rationale,sourceRefs,inputFingerprint}`: `HookRequired` generates the required observation-only hook; `HookNotRequired` records positive source-backed coverage and deliberate no-hook configuration; `Unresolved` needs authoritative resolution, and HITL only for a residual genuine user-owned issue. Hook absence or a previous generated hook supplies no authority. Reconcile decision/configuration before invoking. Technical implementation choices trigger installer convergence.
3. **PLATFORM SELF-CHECK:** run `npm test` from the installed distribution for the pinned synthetic smoke, with explicit `VERIFICATION_SELF_CHECK_ROOT` (unused consumer-owned output path), `VERIFICATION_EXECUTION_ID` and `VERIFICATION_ATTEMPT` matching the reserved dispatch. The smoke reports its `self-check.json` path; retain its terminal success and digest-bound report for adoption evidence. It uses the indexed canary and controlled synthetic browser/session in an isolated scratch root and emits two preflight records; it never establishes consumer READY. If ordinary dependency/runner smoke evidence remains valid and only the hook mechanism needs checking, call `installedHookSelfCheck(binding,resolution,unusedOutputRoot,executionId,attempt)` through `/invocation`. Reuse a still-valid self-check report rather than duplicate proof or rerun it during unrelated consumer repair.
4. **CONSUMER READINESS PROBE:** call `invokeReadiness(request)` below using the actual consumer fixture/runner, current assignment and real consumer hook configuration. Follow its one execution to terminal completion. This executes BrowserPreflight → project stage → TargetPreflight → ENVIRONMENT READY, then normal worker teardown. It writes only readiness records/summary. No product test is selected; no product PASS is produced.
5. **ADOPTION ASSESSMENT:** compare evidence to all applicable readiness prerequisites. READY alone does not prove unrequested custom fixtures, every provider/native operation or omitted project conditions. Record source-backed coverage/evidence and any unresolved prerequisite. Verify integration and frontend configuration against current bytes. Run `validateAdoptionAssessment(checkpoint,assessment)`, then reference the digest-bound assessment and save a completed PASS checkpoint. If validation fails, diagnose rather than weakening requirements.

## Public helper use

Import helpers from `@verification-platform/support/invocation` when configured as a dependency, or the explicitly selected `<distribution>/dist/runtime/invoke.js`. Ordinary JavaScript API calls are the installation tools; they do not install application code or grant permissions.

```js
const checkpoint = createAdoptionCheckpoint(consumerRoot, binding, inputFingerprint);
let digest = writeAdoptionCheckpoint(checkpoint, null); // new file only
const saved = readAdoptionCheckpoint(consumerRoot, binding, inputFingerprint);
// Modify only the current checkpoint fields, then save with saved.digest.
// Compare-and-swap prevents overwriting another installer; stale locks need reconciliation.
```

`reserveAdoptionDispatch(checkpoint,{executionId,attempt,kind,inputFingerprint,commandFingerprint})` returns a checkpoint with reserved dispatch intent. Save it before invoking the check. When the caller receives a tool handle, persist `status:'running'` and that exact handle. Use existing execution-following rules to follow it; lost/unknown dispatch outcomes are BLOCKED until reconciled, never implicitly relaunched. `adoptionResumeAction` returns continue, follow, HITL, BLOCKED, complete or cancelled. HITL/BLOCKED require the nonterminal decision flow below. Complete requires verified PASS; cancelled ends the workflow only after explicit user choice. A stored state is not fresh permission or readiness proof.

A pending request requires `status:'waiting'`, and waiting requires a pending request. Under the existing lock and compare-and-swap, the writer rejects clearing/replacing a persisted request without its matching offered-option resolution and explicit decision reference. Save that resolution with no pending request before creating any later request; unchanged waiting saves remain valid.

Explicit user decline remains represented by `status:'cancelled'`. The checkpoint writer enforces persisted cancellation under its existing lock and compare-and-swap check, even if a caller clears the resolution or supplies a newly created active checkpoint. A future fresh installation must be a distinct adoption workflow; ordinary writes provide no reopen operation. Active-dispatch information remains available for lifecycle finalization.

After the terminal check, use `recordAdoptionCheck(checkpoint,{path,sha256})` and save with the previous digest. It verifies report scope and current dispatch/release identities. For failed input validation or interrupted execution, preserve raw terminal diagnostics, reconcile effects and diagnose further authorized adaptation; never invent a passing report. Successful integrity/self-check/readiness references are kept in the assessment evidence, not a new history system.

`invokeReadiness` requires:

```js
{
  cwd: consumerRoot, planPath, binding,
  resolution: {root: distributionRoot, indexPath: 'resource-index.json', mode: 'execution'},
  assignment, environmentId, claimIds, hookDecision, inputFingerprint,
  runnerEntry, // explicit generated Node-invocable entry under .verification/integration/
  probePath, // explicit generated setup-only probe under the same directory
  sources, // digest-bound current native/bridge source references, including transitive setup inputs
  projectName, // required when the consumer runner declares multiple projects
  requiredFixtures: [], // explicit safe consumer readiness fixtures, if any
  executionId, attempt, deadlineMs
}
```

The assignment selects generated fixture/runner/provider entries and declarations under `.verification/integration/` and the actual host/target/effects/ownership. Claim IDs must exist in the original plan for the environment. Platform validates confined inputs/identities and discovers callable providers before dispatch. It invokes `node <runnerEntry> <request.json>` with the existing bounded deadline/process lifecycle. No Platform source generation, native config import/overlay, filename/extension assumption or fixed typecheck recipe is involved.

The prepared JSON contains the request plus `identity`, original `planBytes`, unique `testKey`, explicit absolute `probePath`, retained `outputRoot`/`summaryPath` and current digest-bound `sources`. The generated entry owns compatible loader/runner invocation, passes that context to its generated config/fixture/probe, preserves native setup/teardown, and finalizes owned child processes normally. Compose the shared fixture through ordinary `test.extend`; select exactly one annotated setup-only probe, one worker, `fullyParallel:false`, zero retries and no product bodies. Adapters/bridges handle module formats, TS/JS and incompatible native runner shapes without removing required semantics.

Generated config calls `recordReadinessConfiguration(prepared, use, projectName)` through `/invocation` to validate concrete assignment/host/target/hook inputs and record effective configuration; use its returned readiness selection in `use.preflight.readiness`, and supply `use.executionIdentity`. Configure `ReadinessReporter` from `<distribution>/dist/runtime/adoption-readiness.js` with the prepared context and `outputDir:<outputRoot>/records`. The reporter validates actual configuration, fixture acknowledgement, probe annotation/source, four stages, hook evidence, source freshness and normal teardown. Before returning, the generated entry records the actual child runner exit in `readiness.json`'s `runner.exitCode`; keep the reporter's actual runner status. Entry-process success alone cannot hide runner failure. Platform retains entry exit/timeout diagnostics separately.

Output is `<assignment.outputDirectory>/adoption-readiness/<execution-id-hash>-<attempt>/`; assign `.verification/adoption-evidence/` as the retained output directory. It contains request JSON, effective inputs, `records/` sidecars and `readiness.json`, never executable integration source. Existing attempt directories refuse relaunch. Keep historical evidence during regeneration and revalidate applicability. Check PASS, actual runner status/exit and normal completion; the product reporter/reconciler is not used.

The assessment passed to `validateAdoptionAssessment` contains `{inputFingerprint,bindingDigest,resolution,frontendConfiguration,integration,selfCheck,readiness,prerequisites,unresolved}`. Evidence fields are `{path,sha256}` references confined to the consumer root; `readiness` is a list for applicable environments/targets. Each prerequisite contains `{sourceRef,reason,evidence:[...]}`. Enumerate applicability from Platform requirements and the native information needed to realize them; this coverage report is not a prerequisite DSL. Keep `unresolved` explicit and empty only when the governing sources and current evidence establish readiness. Self-check and consumer readiness scopes are validated independently. Store assessment JSON as evidence, set `checkpoint.assessment` to its reference, clear active dispatch/pending HITL and set stage PASS/status completed before the final atomic save.

Platform defines WHAT consumer integration must satisfy; the AI installer determines HOW from the current packaged contract and current native consumer sources. Native consumer code/configuration is the semantic authority. On every install, upgrade and recovery, freshly regenerate all required integration under `.verification/integration/`, even when old generated wiring appears valid. All integration-only files, including runners, fixtures, providers/declarations, readiness entries/probes, hooks, adapters and auxiliary bridges, are installer-owned generated output in this single directory. Previous generated integration has no preservation or requirement authority. Autonomously adapt/wrap/bridge/rewire technical incompatibilities within existing authorization. Confine writes by realpath; an escaping symlink is not ownership. Preserve native semantics, installed Platform bytes, checkpoint/approvals and retained evidence. No ownership registry, migration or old-layout cleanup is required. Reconcile active dispatches and reserved correction postconditions before replacing code; never replace code used by a running attempt. Recovery must freshly derive integration even after a completed configuration stage; identical current bytes may reuse still-valid evidence, while changed sources/configuration require fresh affected checks.

## Generated product-execution wiring

CONFIGURE CONSUMER also realizes the existing product-execution entry under `.verification/integration/`, deriving its filenames/module/loader configuration from current native sources. Platform defines the integration requirements; the consumer supplies authoritative proof JSON/configuration/authorization. Integration owns no proof requirements, permission grants, tasks or workflow decisions. No SpecKit, Solo or governance product is needed, and adoption readiness never selects product proof bodies.

The generated entry accepts the ordinary `Invocation` and explicit local `ResolutionConfig` from any compatible caller. Use the pinned public `/resources` and `/validation` APIs for release/input identity, `/compilation` `discoverProviders` and `validateBundle` with actual files/types/readiness, then `/invocation` `invokePlaywright` for valid authorized runnable entries. Bundle validation already calls shared coverage; do not copy it or implement another readiness predicate. Compose the fixture with ordinary `test.extend`, actual configured exports and the existing assignedPage/preflight boundary. Adapt consumer module/loader/runner shapes within authorization; missing generic capabilities do not authorize product instrumentation.

Supply readiness for the exact mapped `(capabilityId, capabilityVersion, environmentId)`, observed for the current configured descriptor/source. The existing `capabilityReadiness` emits the descriptor version. Versionless legacy records remain readable but cannot grant availability; collect current evidence rather than infer or relabel it. Return actual `valid`, `fullyReconciled` and diagnostics through normal caller/tool output. Invalid bundles cannot execute as validated proof; valid partial bundles retain all blockers while independent supported entries run. The zero-runnable case uses existing blocked finalization. Mechanical `fullyReconciled` does not establish semantic decomposition completeness: the AI execution frontend performs the original-proof-to-code audit using existing source/step/assertion references. No new review file/flag or reconciliation state is required.

Preserve original runner/acceptance exits, reporter annotation/source joins, result/manifest, claim records, evidence envelopes/raw attachments and valid source/output roots. Product PASS needs actual proof under semantically reviewed assertions/evidence; setup READY and mechanical reconciliation alone cannot create PASS. Return existing `InvocationReturn` fields/status/paths/diagnostics, not an integration-specific execution-plan JSON. Consumer publication and workflow completion remain optional downstream policy.

Authorized missing/incompatible wiring returns to the existing installer for regeneration/adaptation after active attempts/effects are reconciled. After technical or human-approved resolution, the execution frontend revalidates affected inputs/readiness, regenerates/recompiles and re-audits affected tests, then reassesses through the same APIs. Retain mandatory blockers while an unresolved capability/permission/owner action is pending; never relaunch unchanged failures or repurpose installation checkpoints as product-verification tracking. Real consumer remediation remains separately authorized.

## HITL interaction boundary

Before HITL, exhaust safe and authorized autonomous resolution: reuse authoritative configuration, derive selected values, discover supported current state, regenerate integration, and create/update installer-owned integration within existing authority. Validate the resulting state. A missing technical value alone does not justify HITL. Do not request discoverable/derivable raw technical values such as paths, executable paths, IDs, URLs or configuration filenames.

Each HITL addresses exactly one current unresolved user-owned issue (decision, authorization or external action). Investigate the actual available solutions first and present concrete outcome choices. Each non-cancel option states its outcome, material consequences and the installer's technical implementation within verified authorization. Always include exactly one cancellation option whose description is exactly **Cancel Verifier installation**. Skip, Ignore, Continue partially configured and Continue without required readiness are invalid readiness-bypass substitutes.

For a required external artifact/capability the installer cannot create under current authority, identify the missing prerequisite, external action and owner. Keep the request pending until the user reports completion; then the installer must discover and validate the resulting state before advancing. Do not request transcription of discoverable technical details. After an approved outcome, persist the matching resolution before implementing installer-owned work. After every autonomous or user-approved resolution, validate and reassess before any subsequent HITL; selected outcomes may determine several derived values and eliminate later questions. Reuse unaffected valid evidence and allocate fresh affected checks when required; do not pre-build a questionnaire, condition queue or fixed prerequisite checklist.

At the caller's actual outgoing interaction boundary, use `adoptionResumeAction`/`pendingHITL`: **pending HITL → emit/present only the recorded current HITL → return and wait; otherwise → normal report**. The HITL branch must not fall through to normal reporting. Include only context necessary for the current decision/action and its exact cancellation option; never mix progress/results with a HITL response. Keep detailed progress/diagnostics in existing evidence and report them separately after resolution. On resume, present the restored request unchanged and wait for the explicit decision or requested external-action completion report. This repository delegates emission to the AI/caller; checkpoint validation cannot control arbitrary caller prose.

## Continued convergence, HITL and resume

When diagnosis establishes an authorized adaptation, call `reserveAdoptionCorrection(checkpoint,defectId,diagnosisEvidence)` and save before correction effects. The helper does not perform repairs or authorize them. Preserve the diagnosis, intended correction and actual before/after fingerprints in evidence. Inspect postconditions after interruption; never blindly repeat a reserved correction. Mark the observed correction applied, reassess affected input fingerprints, and start a fresh affected check.

If a genuine user-owned decision, authorization or external action remains after authorized technical convergence, present concrete viable resolution options and always include an explicit option to cancel the entire Verifier installation. Call `requestAdoptionHITL(checkpoint,{action,reason,scope,authorizationReference,options})` and save the waiting checkpoint before asking through the caller's normal HITL interaction. Each option has `{id,action:'continue'|'cancel',description}`; provide distinct IDs, at least one concrete continuation option and exactly one explicit cancellation option described as `Cancel Verifier installation`. The reference identifies the request/applicable authorization, not a grant of permission. An externally dependent option must identify the required decision/action/owner; do not invent a workaround for a platform defect.

Wait for the user's actual decision. Silence, elapsed time, denied authorization and a failed intermediate check do not select cancellation. Before continuing, reconcile any active dispatch and reserved correction postconditions, then call `resolveAdoptionHITL(checkpoint,selectedOptionId,userDecisionReference)` and save. A non-cancel choice records the latest resolution, clears the pending request and resumes active installation; the installer implements the approved option itself within verified authorization, then rechecks. Only an owner-exclusive action is left to that owner, and the installer verifies it and continues afterward. A revised authorized adaptation of the same diagnosis can be reserved without HITL after prior effects/postconditions are reconciled. Keep before/after fingerprints and revised diagnosis/adaptation evidence; never overwrite an unreconciled reservation; unchanged automatic retries remain prohibited. Detailed diagnosis/decision/correction history stays in evidence.

BLOCKED records demonstrated contract inability or a genuine unresolved user-owned prerequisite; technical incompatibility and failed checks alone do not set workflow BLOCKED; it is not a terminal "Verifier not installed" result. The workflow continues until verified PASS or explicit user cancellation. Cancellation is recorded as status `cancelled`, cannot resume or dispatch work, and does not itself authorize uninstall, rollback or browser cleanup. A cancel choice can be recorded even with an unresolved active dispatch; preserve its identity/handle for finalization through existing lifecycle rules, never relaunch it. No generic repair engine, retry quota, permission expansion, check weakening, product-code change or speculative persistent browser setup is permitted.

After HITL, verify the actual supplied action/authorization, revalidate inputs, reconcile any active operation, resolve through the existing helper and persist the decision before approved work, then continue the same workflow with a fresh affected attempt. Do not resume at TargetPreflight using stale browser/project observations. Preserve unaffected valid release/self-check evidence. Do not copy old checkpoint state to a changed release blindly; reconcile its selection and reassess affected stages. Unknown checkpoint formats need explicit reconciliation, not a migration framework.

## State and proof invariants

Fresh install, upgrade and recovery share this regeneration procedure. Readiness hooks observe rather than perform persistent setup; the installation agent performs authorized setup/remediation outside the hook. All browser/profile/pages, including created pages and partial setup state, survive successful/blocked readiness and ordinary teardown. Cleanup/reset/CLOSED baseline is an independently authorized lifecycle action. Temporary clients/owned relays finish normally.

PASS requires valid installed release, successful installed self-check, realized callable consumer integration, resolved hook decision, current completed READY evidence and no unresolved applicable readiness prerequisite. Product evidence/results and Human Acceptance remain separate. Synthetic self-check output cannot satisfy consumer readiness; ENVIRONMENT READY cannot satisfy product proof.
